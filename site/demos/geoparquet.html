GeoParquet

Vector features from a columnar file on plain storage — decoded in the browser, rendered like GeoJSON. The 4,522 trees below travel as 121 KB; the same data as GeoJSON is 2.6 MB on the wire.

Try it: open the network tab and reload — the whole tree cadastre of Vienna's first district arrives as one 121 KB file. Hover a tree for its species, click for the full record, and use "zoom to layer" on the district boundaries: the extent comes from the file's own metadata, no coordinate scan needed.

Configuration

A geoparquet layer is a geojson layer with a url instead of data — styling, clustering, popups and hover tooltips are the same options, because after decoding, the features run through the same pipeline.

          The transfer story, measured on this page's tree layer: 2.6 MB as raw GeoJSON,
          215 KB as gzipped GeoJSON, 121 KB as GeoParquet. The compression lives inside
          the file, so a plain bucket with no Content-Encoding configuration still
          serves the small number — and the browser parses a compact columnar buffer instead of
          megabytes of JSON text.
        

        

          WGS84 only, whole-file loading.
          Coordinates must be OGC:CRS84/EPSG:4326 (the GeoParquet default) — a file in another CRS
          fails with a clear per-layer error naming it; there is no client-side reprojection.
          And like a GeoJSON URL, the whole file is downloaded and decoded: well suited up to a few
          MB / a few hundred thousand features, not a streaming format. For city-to-country-scale
          vector data, cut vector tiles instead (PMTiles works from the same kind of bucket).
        

      


      

        
Producing GeoParquet

        

          Any recent GDAL or DuckDB writes valid GeoParquet — including the WGS84 reprojection and
          the metadata this layer type relies on:
        

        
          ogr2ogr -f Parquet trees.parquet trees.gpkg -t_srs EPSG:4326

        
          INSTALL spatial; LOAD spatial;
          COPY (SELECT * FROM ST_Read('trees.geojson'))
            TO 'trees.parquet' (FORMAT PARQUET, COMPRESSION SNAPPY);

        

          The files on this page come from the City of Vienna's open-data WFS, converted with
          DuckDB exactly like that (district boundaries simplified to ~20 m for size). Snappy,
          gzip, brotli, zstd and lz4 compression all decode; plain Parquet without the
          geo metadata is rejected with a message saying how to convert it.
        

      


      

        
When to reach for GeoParquet

        

          It fills the gap between GeoJSON and vector tiles: the publishing simplicity of a single
          file on any static bucket — no tile cutting, no server — at a transfer size that keeps
          medium datasets comfortable on mobile connections. It is also what modern data pipelines
          already speak: the file your data engineer hands you renders directly, attributes intact,
          no export step. For datasets that outgrow it, PMTiles (vector tiles in one file, also
          server-less) takes over.
