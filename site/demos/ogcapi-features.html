OGC API Features

WFS's successor: plain URLs, plain GeoJSON, paging built into the protocol. A collection URL in the config is all it takes — map0 walks the pages by following the response's own next links.

Try it: open the network tab and reload — the ~2,600 railway stations of Great Britain arrive in pages of 1,000, each next page addressed by the link the previous answer handed back. Hover a station for its name; the airports load in a single page.

Configuration

The url is the collection URL — the thing an API's landing page links to; map0 appends /items and asks for GeoJSON. Everything after the fetch is the geojson pipeline, so style, cluster, popup and hover are the same options as everywhere else. 


      


      

        
What this demo shows

        
    
          
  • An ogcapi-features layer needs nothing but the collection URL
    • 
          
  • Paging follows the response's next links — the spec's own mechanism, so a server capping limit just produces more pages
    • 
          
  • limit (default 10,000) caps the total; pageSize (default 1,000) sizes each request
    • 
          
  • params appends query parameters — bbox, datetime, CQL2 filter, properties
    • 
          
  • API errors are JSON problem details — their title and description land in the layer's error state
    • 
          
  • Styling, clustering, popups, hover, promoteId — exactly the geojson options
    • 
        

        

          Deliberately link-driven.
          The feature count (numberMatched) is optional in the spec and missing from
          real services — this page's own data source omits it. The next link is what
          the standard guarantees, so that is what map0 follows; it also makes offset arithmetic
          the server's problem, not the client's. Features arrive in WGS84 (the API default), which
          is exactly what MapLibre renders. CORS headers are required, as for every browser-read
          source.
        

      


      

        
When to reach for OGC API Features

        

          Same live-data trade-off as WFS — every load asks the
          service, so the map follows the database — but with the friction removed: no version
          negotiation, no outputFormat guessing, no exception XML, and paging that
          works the same on every implementation. If a service offers both interfaces, prefer this
          one. For static snapshots, GeoParquet transfers the
          same data far cheaper; beyond the limit ceiling, cut vector tiles (PMTiles).
